# 检索层自己的度量

端到端召回分不清是检索错还是深挖错：一条条款没被检索回来，和条款回来了但模型没理它，在报告上长得一样。所以先单独量检索。

做法：语料里每条「该命中的条款」标一个可接受集合（打印密码同时违反「认证失败的日志」与「不得写标准输出」，两个都算对，逼它二选一等于量运气），跑初审，按 `pol-` 编号在计划里的先后算名次。

五个标记用例（其余四十四条不标，只统计有没有意外命中）：

| 用例 | 该命中 | 纯嵌入 | 嵌入 + 词面加分 | 条款附示例（代码比代码） |
|---|---|---|---|---|
| case-insensitive-password | pol-security-2（口令比较） | 未命中（回了 pol-security-1） | 未命中（回了 pol-security-1） | 第 1 |
| password-content-equals | pol-security-2 | 未命中（回了 pol-security-1） | 未命中（回了 pol-security-1） | 第 1 |
| policy-plain-equals | pol-security-2 | 未命中（回了 pol-security-1） | 未命中（回了 pol-security-1） | 第 1 |
| password-logged | pol-security-1 或 pol-logging-1 | 第 1 | 第 1 | 第 1 |
| policy-stdout-in-audit | pol-logging-1 | 未命中（没过阈值） | 第 1 | 第 1 |

顶一命中：纯嵌入 1/5，加词面加分 2/5，条款附示例 5/5。条款总数只有五条，所以这不是「检索困难」，是「检索没起作用」。

第三列不是「多加了个示例」那么简单，中间走过几条弯路，都记在这里：

第一版把示例和正文放在一起，取这一条款所有向量里的最高分。结果顶一回到 4/5，但四十四条无关用例里三十八条也命中了——示例代码长得都像普通 Java，什么改动都能蹭上。加了「示例命中再加零点零六分」，正好把整池水拉过阈值。

第二版把查询也拆成两半：中文描述比条款正文，改动代码比示例代码，各走各的空间。这时顶一反而掉回 2/5。原因是查询里的中文描述本身就含「口令」这类词，它能命中兄弟条款的正文；于是又把代码那半分抬到零点七权重，仍然是 2/5——两个条款的加权分只差千分之三。

第三版看了每个条款的两种分数才明白：口令比较这一条，脚本分数上代码吻合度 0.657、正文吻合度 0.486；兄弟条款是 0.604 与 0.599。正文那一半在帮倒忙，它把「认证失败」这条条款顶上来，就因为两者都写着「口令」。所以带示例的条款只用示例算分，没带示例的条款退回用正文算分，正文不再参与带示例条款的比较。

改完顶一 5/5、平均名次 1.00，无关用例的意外命中从 7 涨到 13。代价写在这里：多出来的六条是噪音，落在模型提示词里会占词元、也可能引出偏题的疑问，但比调错条款要便宜。

还有一个坑值得说：示例里的注释是中文，第一版直接把整段示例拿去嵌入，注释又把示例拽回文字空间了。现在示例嵌入前先剥掉注释行。

最值得看的一行是口令比较：三例全错到同一个兄弟条款。「认证失败的日志」与「口令比较」在同一份文档里，前者正文里也写着「口令」两个字，代码里的 `password`、`equals` 就把它顶了上去。这正是代码与文字跨模态匹配的偏差——不是分数不够高，是分错了对象。

复现：`java -cp "target/classes;<classpath>" com.codereview.agent.eval.PolicyRetrievalEval target/eval-corpus`

## 让模型把改动写成一句话，再拿这句话去搜条款

同一批五条标记用例，加了第四个方案：每个改动让 DeepSeek 写成一句中文（不带代码、不带变量名），再拿这句话去比条款正文，比完取顶一。五次调用，几分钱。

| 方案 | 顶一命中 |
|---|---|
| 纯嵌入 | 1/5 |
| 嵌入 + 词面加分 | 2/5 |
| 模型抽象成一句话再搜条款 | 3/5 |
| 条款附示例、代码比代码 | 5/5 |

三条成功的是它把改动说成了条款自己的话：`把用户名和密码明文打印到标准输出`、`按字符序列比较改为按对象相等性比较`、`日志输出方式改为直接打印到标准输出`。

两条失败的也说清了失败原因：`校验密码时由区分大小写改为不区分大小写`、`认证校验从无条件通过改为要求用户名与密码内容一致才通过`。这两句都没有出现「比较方式」「相等性」这类词，反而出现了「校验」「认证」「内容」——它们落在「认证失败的日志」那条条款的正文附近，得分 0.562 和 0.665，对的那条只有 0.534 和 0.497。

所以问题不是条款分不开，是抽象这句话落在了哪个词上：说成条款自己的行话就分得开，说成领域泛词就分不开。这也解释了为什么最初那条模板查询一条都不中——它没有任何行话。

完整输出在 `eval/abstraction-probe.txt`。

结论对设计的影响：代码比示例这条路留下当主力；抽象这条路不进初审主流程（每单元一次模型调用，还比代码路弱），只对没有示例的条款当退路，或者放到深挖里做成调查者可调的工具。

下一步：示例命中是否直接触发必查。现在它只是分数更高，档位仍由「强制条款命中」决定；要不要把「示例吻合到某个程度」也当作强制，得看端到端评估里多出来的噪音会不会盖掉收益。

## 抽象搬进深挖：搜条款、读条款，以及「引用要能对回原文」

上一节最后留的退路做成了两个工具，放在深挖里，初审主流程不碰：搜条款收一句话（比如「口令比较 恒定时间」），返回最像的三条，每条给编号、标题、一小段摘录，分数低于 0.45 就当没搜到；读条款收一个编号（比如 pol-security-2），返回这条的全部正文和它在哪个文件。仓库里没有 `docs/policies` 时两个工具都不出现。初审那边的索引同时从「嵌入 + 词面」换成只按示例打分：有示例的条款拿改动代码比示例代码，没示例的才退回正文。

引用检查分两半。第一半是编号得真实存在；第二半是结论里必须出现条款原文的一段。编号写在 evidence 里算引用，只写在句子里也算——本地模型第一版就是这么绕的：句子写「不符合 pol-logging-1 的规范」，evidence 只填 `ev-1`，检查只认 evidence 时它完全不受约束。

第二半的尺度调了两次。最初按「连续八个字符」比对，本地模型一句「生产环境中直接使用 System.out.println 输出日志，而没有使用日志框架，不符合 pol-logging-1 的规范。」就混过去了：条款里写「…使用日志框架，不允许…」，结论里写「…使用日志框架，不符合…」，八个字符「使用日志框架，不」两边都有，于是「没抄原文」被判成「抄了」。现在中文条款按连续十个汉字比对，标点和代码不参与，所以共用 `System.out` 也不算抄。八个汉字会撞上常用措辞，十个不会。

拿本地模型跑这两条政策用例试了措辞。7B（qwen2.5-coder:7b）两条都停在五次工具调用上限，零结论；3B（qwen2.5-coder:3b）给出一条「…不符合 pol-logging-1 的规范。」，被校验以 `the statement cites pol-logging-1 but does not quote any of its wording` 拒掉；它接着把编号删掉重试，这次因为行号 42 不在单元 43–45 内、也没有证据覆盖而被拒。也就是说，门控对小模型起的是「不许糊弄」的作用，但小模型写不出能过门的结论——想看清措辞变化要用更强的模型或线上接口。另外这两个本地模型一次都没调用搜条款/读条款，工具是给会用的调查者的。

复现（只跑这两条用例）：

```bash
java -cp "target/classes;<classpath>" com.codereview.agent.eval.EvalRunner <workspace> <out> \
  --ollama --only=policy-plain-equals,policy-stdout-in-audit
```

### 换成线上模型再跑

上面那句「要用更强的模型或线上接口」这次补上了：把密钥放进环境变量后用 deepseek-chat 跑同样两条，引用检查两条都过了——结论里都写了条款编号，也原样抄了十个汉字以上的原文（「口令必须使用恒定时间的比较方式，禁止使用 equals 或 equalsIgnoreCase」「生产代码使用日志框架，不允许 System.out 或 System.err」）。挡下它们的换成了更早那条符号检查。

两条被拒的原因不一样，但都不是引用本身。口令那条建议改用 `MessageDigest.isEqual`，这个类名是模型自己的知识——读条款只返回正文，条款里的正例代码（示例块）不在正文里，也就没进证据，于是「证据里没出现过这个名字」成立。标准输出那条建议把日志改回 `log.info("audited order {}", …)`，而 diff 原文是 `log.info("audited order {} v2", …)`，差一个参数，verbatim 对不上。两句重试后仍是同样结果，两条用例都以「降级、零结论」收尾。

两次工具调用值得记一笔：口令那条先读代码、再读 pol-security-2，标准输出那条只读了代码；两条都没有调用搜条款。

这暴露的是门控和「给改法」之间的张力：结论要引用条款、又不能凭空写没见过的 API，而正确的改法往往正是条款示例里的那个 API。可选的收法有三条——提示词里把反引号规则说得更死，让改法用文字描述；读条款把示例一并返回；或者接受「改法可以只描述、不写代码」。这次先按现状记录，没有为了让它过门去调提示词。

### 把示例还给调查员

按第一条改了一版：读条款现在返回这条的正文连同它自己的示例代码，校验方信任的条款文本也一并含示例——模型读到的条款和校验按的条款是同一份，抄自条款示例里的名字不再算「证据里没有」。

口令那条重跑之后结论落地了，成了正式结论而不是降级，措辞是：「check 把口令比较从 contentEquals 改成了 equals，属于逐字符提前返回的比较方式，违反 pol-security-2：「口令必须使用恒定时间的比较方式，禁止使用 equals 或 equalsIgnoreCase」。请改回恒定时间比较（如 MessageDigest.isEqual 比较摘要）」——它建议的那个方法正是条款示例里写的，之前读不到示例时同一个建议被判成编造。

标准输出那条当时仍降级，原因和示例无关：它建议「改回原来的 log.info」，写出来的那行漏了原文里的 v2 参数，逐字对不上证据——撞上的是更早那条「反引号里的代码必须原样出现」的规则。

这条也放宽了一点：多名字的代码片段，只要其中的标识符按同样的顺序都出现过，就算「见过」，不再苛求整行逐字一致。理由是这类建议往往就是把证据里那行凭记忆重写一遍，少一个参数、换个引号，名字却没有一个是编的；而凭空冒出来的名字仍然过不了，因为它不在任何证据或 diff 里。放宽之后重跑，标准输出那条也落地成了正式结论：「audit 把原来的 log.info 换成了 System.out.println，违反强制条款 pol-logging-1：「生产代码使用日志框架，不允许 System.out 或 System.err。」请改回用日志框架输出，例如 log.info("audited order {}", order.getName())」。两条一起跑：findings 2、downgraded 0，两条都算有证据支撑。

复现（需要 `CODEREVIEW_LLM_API_KEY`，嵌入仍走本地 Ollama）：

```bash
java -cp "target/classes;<classpath>" com.codereview.agent.eval.EvalRunner <workspace> <out> \
  --real --only=policy-plain-equals,policy-stdout-in-audit
```
